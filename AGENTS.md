# Rexume

Rexume reopens, in the panes Rex restores after its server stops, the Claude Code, Codex, Pi, or omp conversation each pane ran, and carries task results from worker panes back to the orchestrator conversation that registered them. One job, `rexume daemon` under launchd or systemd, observes the server; hooks, restored panes, and task commands are short processes writing the same SQLite state. [docs/design.md](docs/design.md) explains the states restores, tasks, notices, and cleanup go through, and what each records before its side effect.

## Goals

- **A pane the user closed stays closed; everything else comes back** after a Rex crash, a server restart, or a normal stop. The only accepted loss is a change the machine had no time to save.
- **Continue only what the server's end cut off, exactly once.** A finished, cancelled, or waiting conversation reopens without a new turn, and no conversation runs in two panes. Rexume decides this from the runtimes' own records, not from each agent's resume setting.
- **An unknown side effect is never repeated.** A typed line, close, or notice that may have happened is reconciled from claims or the owner's own record, or left visibly `unknown`; it is not retried to make a state look complete.
- **A worker's result reaches its owner, and only an unused disposable worker's pane is closed.** An acknowledged worker and a pane someone took over are different states and stay distinguishable in the schema.
- **No work while nothing changes.** Rexume's own code sets no timers, does not poll, and starts no process per event; with nothing changing, the daemon does not wake. `rex do` is Rex's program, and its runtime's own wakeups are not Rexume's to remove.
- **Restored soon.** The conversations of 20 sessions the server restored reopen within about a second of the new server starting. `tests/it/bench.rs` measures it, and memory, which has no target but is reported with any change that may move it.
- **Install once, then forget it.** `rexume install` owns every hook and launchd or systemd resource Rexume needs. Running it again leaves one copy of each entry, nothing left over from an earlier install, and the user's other settings as they were.

## Decisions to keep

Each holds as long as its reason does.

- **Unsafe code only in `src/proc.rs`.** Rexume denies unsafe code crate-wide, so that what the compiler cannot check stays in one small module, and allows it there, on macOS only, for `libc::proc_pidinfo`, which reads a process's parent and name, and `libc::sysctl` with `KERN_PROCARGS2`, which reads its arguments and the environment it started with; Linux reads them from `/proc`. `ps` would be a fork per report, and the `libproc` crate's build script runs bindgen with a hard-coded Command Line Tools SDK path, which would make CI and bottle builds depend on that path. Every unsafe block carries a `SAFETY` comment (`undocumented_unsafe_blocks` is denied).
- **What the product waits on.** The daemon's event loop wakes on its socket, the database's write-ahead log, followed files and process exits, `SIGTERM` and `SIGINT`, and deadlines it computes; `task wait` waits on the write-ahead log. Tests may poll.
- **The daemon's own commits wake nothing.** `data_version` moves only for other connections' commits, so a pane change the daemon records from an event wakes the restores itself, and the first read of a restored pane follows the baseline that records it; otherwise a pane is read again only at its 30-second deadline.
- **`Store::settle` after every write-ahead-log wake.** A commit wakes the log's watchers before readers can see it, so after each such wake the daemon calls `Store::settle` and `task wait` reads inside a write transaction, which takes the same lock; without it a woken reader can miss the commit and sleep through it. `docs/design.md` explains the race.
- **Which panes exist comes from `session.list_blocks`, not `session.view`.** The view leaves out detached panes, where an orchestrator starts the workers nobody watches, so reading existence from it records a running worker as closed and leaves its pane unplanned at a restore. The daemon reads the view only for focus before a close, and takes the revision that schedules the next list from `session_view_changed` events, since the list carries none.
- **The adapter starts its relay with `detach = true`.** Rex stops a script's non-detached commands when the script's top level finishes.
- **One adapter, one server call at a time.** A call the server holds delays every call behind it, even past the 30 seconds the daemon waits for its answer (`docs/design.md`'s limits). More `rex do` processes, each with its own memory and event stream, or a `rex api call` process per call would let calls to other sessions go on meanwhile, at a constant cost, for a case seen only when the server had a fault: a Rex server bug held calls to a just-restored session for about 10 seconds. The daemon's warning for a slow call shows how often it happens.
- **Signals through the event loop.** The daemon blocks `SIGTERM` and `SIGINT` and reads them as kqueue `EVFILT_SIGNAL` events or from a signalfd, then ends `rex do` and exits 0; no signal handler. The job ends the whole process group anyway, but a daemon run by hand or by a test would otherwise leave `rex do` running until the server stops. An orphaned relay exits on its socket's end.
- **One writer per resource, short transactions, no I/O inside one.** Durable state is committed before the side effect it guards (`typed` before the gate's line is written, `closing` before a close, `sending` before a notice).
- **Schema.** One `schema.sql`, which sets the current `user_version`, and a byte copy of each version's schema in `tests/fixtures/schema-vN.sql`, which goes back to the bytes its release shipped once a later version replaces it: `tests/it/schema.rs` compares what the current one creates, not its comments, so a comment change is copied by hand, and the upgrade tests start from the older ones. `STRICT` tables, Unix-millisecond integers, UUIDv7 IDs, and on every state column a `CHECK` that lists its states, so writing any other value fails. `Store::open` tells schemas apart by `user_version`: it upgrades a database of each released version, whose fixture the upgrade tests start from, and refuses one newer than the binary. Every column has a reader or a requirement.
- **Store access.** A function that writes takes `&Transaction`, one that only reads takes `&Connection`. Every value is bound to a placeholder, and no `IN` list's length depends on the data. A partial index's predicate lives in one constant (`task::OPEN` for `task_round_open`) that every query relying on the index uses, because SQLite uses a partial index only for a predicate it can prove matches; `every_pass_statement_uses_an_index` in `src/task/tests.rs` runs `EXPLAIN QUERY PLAN` on the statements every daemon pass runs and fails on a `SCAN` of any table but `task` and `notice`, or when a statement on open rounds stops using `task_round_open`, and checks only the statements it lists.
- **Nothing updates or deletes an archive row, an upgrade included.** `export` lists the archive's keys in the read transaction that reads everything in use and reads each document only after it, so that its output is one moment's state while nothing is printed inside a transaction; a row changed or deleted in between would print another moment's document or fail the export. `data` keeps the shape of the `version` its row records, which a reader interprets through that version's fixture.
- **`enum Runtime` is the extension point** for another agent runtime: its record parser, resume command, and notice transport.
- **`install` adds to the user's files and replaces its own.** The hooks live in the user's own settings, so install recognizes its hook by the command and appends it only when it is missing, leaving every other entry, and a hook the user edited, as it is; it never rewrites existing groups, because Codex keys hook approval by position. The Claude Code plugin's files, the Pi and omp extensions, and the plist or systemd unit hold nothing of the user's, so install replaces each whole through a rename when its content differs and keeps no backup; they are customized through install's flags. The skill stub is replaced the same way, but only where install wrote it: users and other tools keep their own skills in the same directories, so a `rexume` skill without the stub's `Written by` line is left as it is. Install names each file by the path its runtime reads: a write follows links there as that read does, and a removal takes only the entry at that path, never a path with its links resolved, because links are the user's arrangement; resolving serves only to tell whether two paths are one. See `docs/cli.md`.
- **The Claude Code plugin is registered through `claude plugin`.** Claude Code keeps an installed plugin in a registry of its own besides the settings, so writing `enabledPlugins` and `extraKnownMarketplaces` directly would leave entries there that only its commands remove; `~/.claude/skills` is not a plugin location and other agents read it. The plugin trusts any socket line that starts with a Rexume token instead of verifying that Rexume wrote it, so another session's model can forge one with a cross-session message. A check Rexume could leave for the plugin, such as a file per delivery, would stop only a session that can neither write files nor run commands; one that can forges the check or reaches the worker through `rexume task send`.
- **No `GOGC` for `rex do`.** Setting 50 or 25 changed total resident memory by under 1 MiB.
- **A snapshot borrows nothing of the repository and writes nothing in it.** It runs `git` on a copy of the index, with an object directory of its own whose alternates are Rexume's directories alone, never the repository's objects, since Git refreshes the modification time of an object it is asked to write again, in an alternate too; what Git must read from those objects is copied out first. It refuses a split index, whose shared file any read of the index refreshes. The owner's task commands take snapshots, not the daemon, which would otherwise start a process per finished round. A clean or process filter other than Git LFS's runs only denied writes to the repository, under `sandbox-exec` on macOS; Landlock does not deny changing a file's mode, times, or extended attributes (observed on Linux 7.2), so on Linux a snapshot that needs such a filter is not taken. Every filter runs required, because Git stores a file unfiltered when a filter that is not required fails. `src/git/tests.rs` fails when a snapshot changes anything in the repository, down to modification times.

## Develop and validate

- The repository is public, so code, tests, docs, commit messages, and issues publish any session content, conversation IDs, paths, host names, or user names they hold; its fixtures are synthetic.
- Prose names the project Rexume. Literals keep `rexume`: the command, crate, paths, and job names, and the `` // Written by `rexume install` `` line by which install recognizes the Pi and omp extensions it wrote.
- `make check` runs what CI runs: `cargo deny --locked check` (needs network), `cargo fmt --check`, Clippy with warnings denied, and `cargo test --locked`; on Linux, CI runs it with `TARGET` set to each static musl target the release ships, such as `make check TARGET=x86_64-unknown-linux-musl`. CI also runs `actionlint`, which `make check` does not. Workflows name each action by its version tag, and `.github/workflows/actions.lock`, which `gh actions-lock` writes, pins it to a commit; GitHub enforces the lockfile only for the workflows it lists, and CI's `gh actions-lock --verify` fails while the lockfile does not match the workflows.
- Tests of pure functions and in-memory data stay in their module; tests that need a `Store` live in the owning module's `tests.rs` with a temporary database; only tests that need the built binary, the job's service manager, or a Rex server go to `tests/it`.
- Functions stay within Clippy's `too_many_lines` (100 lines, tests included); a test that is one continuous scenario may carry `#[expect(clippy::too_many_lines, reason = "...")]` after its fixtures and observations are extracted. Rust files stay within 300 lines not counting blank and `//` lines, which `tests/it/structure.rs` enforces. Over the limit, the test block moves to `foo/tests.rs` first, then the file splits along an owner seam.
- Integration tests are one `tests/it` binary with a module per behavior and helpers in `common.rs`. There `common::db` opens the state database so that a test's own writes meet the same foreign keys, and `common::query` reads it and fails on a broken query instead of returning `None`. The scenarios that need a real Rex server are `#[ignore]`d, so only `cargo test --test it -- --ignored` runs them. They use `REXUME_TEST_REX`, or else the Rex CLI the app installs on macOS and the first `rex` on `PATH` on Linux. Their servers restore their own sessions, as the Rex app's does, and the harness fails on a Rex CLI without that restore. Each test starts its own server with its own socket, home, state directory, and `REX_SERVER` from a cleared environment, and runs its daemon in its own process group; that harness is what keeps a scenario off the user's server and `~/.local/state/rexume`.
- A development build defaults to the user's server and state directory, the ones the installed daemon uses; `--server` and `--state-dir` point it elsewhere.
- CI runs neither the `--ignored` scenarios, which exercise the event loop, restore planning, and task transitions against a real Rex server, nor the bench, and code under `cfg(target_os = "linux")` runs only on Linux. The bench is `cargo test --release --test it bench -- --ignored --nocapture` on macOS; `docs/design.md` explains its report, which is read beside the baseline commit's from the same otherwise idle machine.
- The guide tells agents to follow it where it differs from Rex's own guide, so a changed `rex skill show` needs a review, which a check on the maintainer's machines reports by comparing `rexume skill status` with the running Rex. Agents get Rex's guide from the running server's `rex`, which a newer build the app has only downloaded may not match. The review reads the old guide's diff against the new one, or the whole new guide when the old text is not at hand, and Rex's changelog since the recorded version; retests each behavior where `guide.md`, `agents.md`, or `runtimes.md` differs from Rex's guide; drops what Rex's guide now covers and revises what it contradicts; and records that Rex's `rex_version` and the SHA-256 of its `rex skill show` in `skills/rexume/rex-guide.json` in the same commit, which a release then ships. Nothing else changes the record: not a new Rex, a build, or an install.
- Commits follow Conventional Commits.
- Releases stay at `0.1.x`, breaking changes included, until the maintainer approves another version.
- Releases are tag-driven. Bump `version` in `Cargo.toml`, add `docs/releases/VERSION.md` (the publish workflow refuses a tag without it), and push a `vVERSION` tag; the workflow reruns the checks, creates the GitHub Release with the Linux archives and their provenance attestations, and asks `Entwining/homebrew-tap` to update its formula. The formula runs `make build`, so the packaging lives in the Makefile.

## Environment traps

- Agent sandboxes block what the integration tests need: signalling and listing processes (`kill`, `ps`, `pgrep`) and Unix sockets outside the allowlist. On macOS they also block `sandbox-exec`, so a sandboxed `cargo test` checks only the snapshot path where a filter's writes cannot be denied; CI's macOS job checks the other.
- An agent a harness starts on a test Rex server still runs the user's installed hooks, which find `rexume` through a login shell that puts the installed binary before the test's `PATH`, so they report into `~/.local/state/rexume`. Claude Code started with `--setting-sources project,local` and a settings file whose hook names the test binary by absolute path reports into the test's state, and so does Pi started with `-ne` and `-e` naming a copy of the extension whose `rexume` command and inbox are the test's. Codex runs hooks through a login shell, and neither a `SHELL` override nor `-c features.hooks=false` kept its hook out of the user's state. The omp extension omp loads from `~/.omp/agent` writes its record and reads its inbox under `$HOME/.local/state/rexume`, so an omp the harness starts with the user's home reports into the user's state.
- A test daemon's `rex do` and relay outlive a kill of the daemon alone; `kill -KILL -- -PGID` ends its whole process group.
- The unit tests of the Pi and omp extensions and the Claude Code plugin run their TypeScript in `node`, which strips types without a flag from Node 22.18 and 23.6.
- The snapshot tests run `git-lfs` from `PATH`.
- The Rex app can keep `RexServer/Versions/Current` on an older build than one it has already downloaded beside it, so the default test CLI can lack a feature the newer build has, such as its own restore; `REXUME_TEST_REX` can name the newer build's `rex`.
- macOS has no `timeout`; `perl -e 'alarm shift; exec @ARGV' SECONDS COMMAND` does the same.
