# How Rexume works

This describes the current design for maintainers and for anyone who needs to know what a state in `state.db` means. The schema with its comments is [`src/store/schema.sql`](../src/store/schema.sql).

## Processes

A job runs `rexume daemon`: a LaunchAgent on macOS, a systemd user service on Linux. The daemon starts `rex do` with the adapter script ([`src/rex/adapter.lua`](../src/rex/adapter.lua)) as its child; the script subscribes to the server's events and starts `rexume relay`, which carries events and calls over a Unix socket in the state directory back to the daemon. One event loop in the daemon, kqueue on macOS and epoll with inotify, pidfds, and a signalfd on Linux, waits on that socket, the state database's write-ahead log, the files it follows, the exits of processes it tracks, the path of its own executable, `SIGTERM` and `SIGINT`, and deadlines it computes; with nothing happening it does not wake. The two signals are blocked and read from the queue, so on either the daemon ends `rex do` and exits; the job ends the whole process group anyway, but a daemon run by hand or by a test would otherwise leave `rex do` running until the server stops.

A commit writes its frames to the write-ahead log, which wakes the processes watching it, before it becomes visible in the log's memory-mapped index, which no watch sees. So after each wake from the log, the daemon and `task wait` take the write lock, which waits for a commit in progress, before they read; otherwise a reader woken early could find nothing new and sleep through the commit.

The daemon alone records panes, drives restores, sends notices, and closes worker panes; hooks, gates, and task commands are short processes that write the same database in short transactions. When the executable at the path the job starts is replaced or removed, as an upgrade does (Homebrew relinks it, Cargo renames a new file over it), the daemon exits and the job starts the new one; restores and notices resume from the database, and the new daemon brings the Pi extension install wrote up to date and adds the Claude Code turn hooks an earlier install left out ([cli.md](cli.md#daemon)).

## What is saved

Rexume keeps everything it saves in the state directory, which only its user may enter: it holds task results and the final answers of Claude Code turns, and every Rexume process runs as that user. Each directory there is created with mode `0700` by whichever process needs it first, since a hook or the Pi extension may run before the daemon, so none is open even for a moment; the files in them keep the ordinary mode, which the directory makes unreachable to others. The daemon also closes a state directory open to other users when it starts, which an upgrade does, so one an earlier version created open is closed without the user doing anything.

The daemon keeps one observation of one server instance as an **epoch**. It ends as `server_gone` when the connection ended and the server no longer answers as the same instance, so the last observed program states are what the server held when it stopped, or as `disconnected` when only the connection ended. Only after `server_gone` can a turn be continued. An epoch the daemon ended on an error, such as one from the database, keeps that error, which a stop or replacement of the daemon is not, and `rexume status` shows the newest epoch's: the daemon connects again after a delay, but records nothing until an epoch holds.

The `live` table maps each server instance's IDs of sessions and panes to **lineages**, the ID each had when first seen. Rex restores its sessions under the IDs they had, so a session or pane first seen on a new instance under an ID an earlier instance bound keeps the lineage the latest such instance bound it to, as long as the earlier instances' bindings are kept, which is until the new instance's sessions and panes are first read. One whose lineage another resource on the instance holds already, as a copy that an earlier version restored beside Rex's own may, gets a new lineage instead, so that both are recorded. The daemon reads a session's view again only when its revision moves past the one it read, at once after a change but at most once per 300 ms, to record the session's panes. A pane closed while the server runs is forgotten in one transaction. On connecting, the daemon compares its records with the server's and forgets panes the server no longer has.

`occupant` records which agent conversation a pane runs, from the session-start hook, and `block` caches the pane's foreground program, program status, and exit. `report` records an occupant only when the reporting agent's parent process is the pane's foreground program, so a run the agent starts in another process does not replace the pane's conversation. Sessions the agent runs inside its own process, such as Claude Code subagents, Codex guardian reviews, and Pi SDK sessions, pass that check, so the runtime's marks decide ([cli.md](cli.md#report) lists them). Codex and Pi mark only their interactive conversations, not their inner sessions, so a start without that mark is ignored while its process already holds the pane; from a new process, such as an ephemeral `codex exec` or `pi -p`, it becomes the occupant, so that `task` commands in the pane name it, and a restore leaves its pane the shell Rex started. A restore's gate records the conversation it starts as the pane's occupant in its claim, as the gate's own process, which the shell the gate becomes keeps for a lone command: Codex runs a resumed conversation's session-start hook only when its first turn starts (observed with `codex resume` on Codex 0.165.0, [openai/codex#51360](https://github.com/openai/codex/issues/51360)), and requests and notices would otherwise wait for input nobody gives. The gate measures the record's start as a report does but cannot know the process's name, so an unmarked start from that process counts as an inner session, and the conversation's own report adds the name and keeps the start. Claude Code's messaging socket comes only with its report, so a send to it before then fails before anything leaves and is tried again on the next pass. A conversation that a shell function wraps, or that is started from a shell, is the shell's child, whose PID the gate does not know, so only its report records its process. A conversation's turns come from its record, which is the authority on them: Codex's transcript and Pi's session file, which Rexume reads line by line and never writes, and for Claude Code a turn record its hooks write in the state directory (`claude/SESSION_ID.jsonl`). Claude Code's transcript names no turn, so it does not show which of its records end one, and it may not hold a turn's final answer yet when the turn ends; its `UserPromptSubmit` hook names the prompt that starts a turn or that the running turn takes in, and its `Stop` and `StopFailure` hooks name the prompt whose turn they end and give its final answer or error. That hook runs before another `UserPromptSubmit` hook can reject the prompt, which then gets no `Stop`, and the next prompt gets a new ID; Claude Code runs no hook for a turn the user interrupts either. So a prompt whose turn nothing ended when the next prompt starts counts as cancelled, interrupted or rejected, and input counts as received only once its turn ends. A `Stop` hook that blocks makes Claude Code go on after its `Stop`, which the record shows only when Claude Code stops again. Each hook appends one line in one write, and keeps no text of a prompt but a leading notice or request token. The daemon creates that directory when it starts, so a record not written yet is followed through it, and the sweep deletes a record no conversation row names once its hooks have written nothing for 30 days. A line that is complete but not JSON is logged with its path and offset, and the turn it belongs to counts as unknown; a line still being written is read once it ends.

`Store::open` applies the schema to a new, empty database, upgrades one an earlier version wrote in place in one transaction, and uses one whose `application_id` and `user_version` match this version without taking the write lock; it refuses anything else, including a database written by a newer version. `rexume status` opens the database read-only, so it refuses an earlier version's database until another command has upgraded it. When the daemon starts observing an instance, it deletes what nothing refers to any more: other instances' `live` rows, panes no open task names, earlier instances' restores, epochs, and conversations older than 30 days, and tasks whose latest round was acknowledged, or if never acknowledged finished, more than 30 days ago and has no notice that may still reach its owner.

## Restore

Rex restores its sessions itself when its server starts again: their windows, panes, and labels under the IDs they had, with a new login shell in each pane. Rexume's part is the conversation each pane ran.

When the daemon starts observing a new instance, before it reads the panes' current state, it binds every session and pane the server shows to its lineage and plans each pane recorded on an earlier instance from that pane's last record there, in one transaction per pane. A pane whose conversation reopens gets one `restore` row; any other pane keeps the shell Rex started, and a task round left open there ends as `terminated` (see [Tasks](#tasks)), except in a pane whose conversation another pane reopens or runs in, or someone reopened there on the new instance, where the round goes on from the conversation's record. The unique index `restore_executor` lets only one pane per instance reopen a given conversation, so a second pane that showed it keeps its shell, unless that pane shows the turn the server's end cut off and the first would reopen the conversation without it: the plan then moves to the second pane.

A pane starts by what it was last used for, as its record shows. The occupant counts only when it reported on the instance the pane's record describes, because a PID names a process only there. An occupant reported before version 3 that the upgrade could not date counts as the pane's.

- `continue`: the epoch ended `server_gone`, the pane's last status came from the same process and was `working`, and the conversation's record shows a prompt that no answer, cancel, or error ended, or, for Claude Code, ends with an answer: Claude Code reports `done` once its `Stop` hooks ran, so one still `working` after the answer its record shows went on as a `Stop` hook told it to. A server that stopped in the moment between that answer and the `done` after it also leaves it `working`, and the conversation gets the prompt then too. The conversation reopens with one continuation prompt carrying a reference, so its record shows the prompt was sent once; the prompt also lists the tasks it registered that are not acknowledged. In Claude Code's turn record that prompt carries on the turn it continues, with the input that turn took in, so a round waiting for the turn takes the answer the continuation finishes with. The gate reads the record again before claiming, from where the plan read it, and reopens without the prompt when a turn has ended since; `restore.started` records what it chose to start, committed before it starts it. A conversation that was a non-interactive run does not continue: its task ended with the server, and a prompt would not bring back its result file.
- `agent`: the conversation reopens without a new turn: it was still the pane's foreground program, or it was the terminal's own program and had exited, and did not run in another pane afterwards. This includes a record with a line that is not JSON, and one that cannot be read: without the whole record, Rexume cannot tell that the turn was cut off.
- Anything else keeps the shell: a shell or another program in the foreground, a program that had exited and was not a conversation, a conversation that had left the pane or that another pane reopens, and a Claude Code or Codex conversation whose transcript does not exist yet: both write it only with the first prompt and refuse to reopen without it. Pi opens a missing session file as a new session, so a Pi conversation reopens with the settings it reported.

Once the daemon has read every pane, it reads each planned pane from the server and types into it once the pane shows the shell Rex started ready for a line: the foreground is a login shell (its `argv0` starts with `-`) with at most one ancestor, the terminal's `login` on macOS, and the pane has not exited; and either the terminal is in canonical mode, as `input_mode` reports it, so the shell still reads its startup files and the terminal holds the line for its first prompt, or a line editor reads keys, the cell before the cursor, found from the cursor's position in the screen as escape sequences, holds no character but a space, and no row below the cursor holds anything. Each character takes its own width there, as Rex lays them out, so a ZWJ emoji sequence counts each of its code points. A prompt ends in a space and text typed after it in something else, so a prompt that does not end in a space keeps the pane waiting. The rows below hold the rest of a typed line that wraps, or the other lines of a buffer of several the cursor was moved back into, which the line would not clear: zsh's Ctrl-E and Ctrl-U act on one line of the buffer, so the others would run with the gate. What follows the cursor on its row, a right-hand prompt or text someone typed and moved back before, the line clears. Until then `note` says what the pane shows, and the pane is read again when its recorded foreground changes or 30 seconds after the plan, since Rex reports no change of the screen; a pane still not ready then is `skipped` and left to the user. Nothing sleeps meanwhile: an event the daemon records wakes the restores, because the daemon's own commits leave the database's `data_version` as it was.

The daemon commits `typed` with `typed_at` before it writes the line, so the line is typed at most once: Ctrl-E and Ctrl-U, which move to the end of the line editor's line and empty it (zsh and bash keep the whole line to yank back; a vi insert mode takes Ctrl-E as a character and kills only what precedes the cursor) or, before the first prompt, the terminal's pending input, so what the check does not read, after the cursor, or typed since, is cleared rather than run with the gate; a space, which keeps the line out of a history that ignores such lines; `rexume gate --state-dir DIR ID`; and Return. A refused write is `failed`, since nothing reached the shell, and ends the pane's open task rounds as if it kept its shell. A write that was answered, or got no answer, waits 5 seconds for the gate's claim and is then `unknown`, which a gate that starts later still claims.

| `restore.state` | Meaning |
| --- | --- |
| `planned` | Waiting for the pane to show its shell at an empty prompt; `note` says what it shows. |
| `typed` | The line is about to be written, or was; never written again. |
| `claimed` | The gate claimed it, and `started` says what it started. |
| `unknown` | No gate claimed it within 5 seconds of the write, which may not have reached the shell. |
| `skipped` | Nothing was typed: the pane closed, the conversation reported from another pane since the plan or on this instance, or the pane did not show an empty prompt within 30 seconds. |
| `failed` | The server refused the write. |

The gate claims the row with a compare-and-set from `typed` or `unknown` and, in the same transaction, binds its pane and records the conversation as the pane's occupant, as the gate's own process, which the row keeps as `pid`, with the record's length as the start of its turns. If the conversation reported itself from another pane at or after the plan's time, or on the restore's instance, as when someone reopened it before the daemon planned, the gate claims the row as `shell` and starts nothing. It then replaces itself with an interactive shell, `SHELL -i -c "VARS COMMAND [PROMPT]"`, so the user's alias or shell function for the agent's command applies as when the user starts it, and without `REX_SESSION` when the conversation ran without it, as a worker does. zsh and bash run a lone command in place, so the conversation keeps the gate's process. One a function wraps runs as that shell's child, maybe after other commands the function runs first: when the pane reports a new foreground whose parent is the gate's process, or that process itself again, as when a startup file's command came first, and the conversation has not reported itself yet, the daemon records that foreground as the occupant instead, because Codex reports itself only when its first turn starts and requests and notices wait for the occupant to be the pane's foreground. When the conversation exits, the pane is back at the login shell's prompt.

Reopening keeps the conversation's settings: Claude Code gets the model and effort it reported, kept from its first start since a resumed session's start omits the model; Codex gets the model and effort its record last applied; Pi reopens an existing session file without flags, so Pi applies its current branch's model and thinking itself. Claude Code also gets the launch flags and provider variables its last report read from its process, as [`report`](cli.md#report) lists them: the variables as assignments before the command, which set them for it alone and, unlike `env`, keep the user's alias or shell function for `claude` when it runs from a shell, and the flags before `--resume`, so a continuation prompt stays the last, positional argument after a flag whose value is optional or variadic. A conversation reopened this way starts with them and so reports them again; one started without them, such as by `claude --resume` by hand, drops them with its next report. Reopening also keeps the permission mode. Claude Code gets the mode its record last shows with `--permission-mode`, read from the end of the record at plan time: Claude Code writes the mode on each prompt and when a turn ends or the session exits, so a mode changed after the last prompt counts, while its own resume starts a session that was in `bypassPermissions` in a new session's mode and a Manual one in a settings `defaultMode`. A record that shows no mode, as an older one may not, leaves the mode to Claude Code's resume, and one that cannot be read leaves the settings the conversation reported. Codex's resume restores the approval policy, approvals reviewer, and permission profile its record last shows unless the command line overrides them (Codex 0.164.0), so Rexume passes none; managed requirements can still narrow them. Pi has no permission modes.

A released disposable worker whose pane is unchanged since its latest result, with no unfinished round of any task on that pane, is not planned: its task holds the pane as `closing`, and the daemon closes the pane, as cleanup closes one, once it shows the shell Rex started at an empty prompt, read as above, with nothing after the cursor but a right-hand prompt, and is not its session's focused pane. Text there counts as a right-hand prompt only when a blank separates it from the cursor and it ends in the row's last two columns, as the pane's `size` gives them; a shell that measures a character otherwise than Rex places it short of the row's end, which keeps the pane. A pane that still shows something else, has focus, cannot be read, or got no answer to its close 30 seconds after the restore began is `kept`; a close that went through marks it `closed` by its event. A worker whose record cannot be read is planned, since the record may show a turn after that result.

## Tasks

An orchestrator conversation registers a worker pane with `task add`, and each result it collects is a `task_round`. A non-interactive worker (`--result-file`) is followed by its process, not by a conversation: its one round ends when the program that was the pane's foreground at `add` exits, and `add` refuses a pane whose program has already exited.

An interactive worker's task follows one conversation, bound at `add` when the pane's program had already reported, otherwise by the daemon once the pane's occupant has reported since `add` or is its foreground program; a conversation that takes over the pane after that is never followed. Its record is a sequence of turns, which the daemon reads in order, yielding each finished turn (answered, cancelled, or failed) with the offset just after it; a turn still open where the record ends is not yielded, so nothing after it is passed over. Each round takes at most one turn, in the transaction that saves its result, writes its notice, and records the turn as taken, and no two rounds of a task take the same turn: a turn is named by where it starts, and an answered one also by its answer's record ID. The task's **position** is the offset up to which every finished turn has been taken; it moves in that same transaction. A daemon or a server restart therefore reads again from the position and takes nothing twice, also when a restore reopens the conversation, as long as its runtime writes on in the same record. The position starts where the record ended when the conversation's process reported, or when a restore's gate started it, as `occupant.start_position` records: Claude Code and Codex wait for the session-start hook before they answer, so the report measures the record then, the Pi extension measures it before Pi sends a prompt, and the gate measures it before the conversation runs. A turn that finished before `add` therefore still counts, and the turns a resumed conversation's record already held are not the task's.

How a round starts decides which turn it takes:

| Round | Started by | Takes |
| --- | --- | --- |
| first | `task add` | the earliest finished turn after the position, the first the worker's process finished |
| next | `task next` | the earliest finished turn after the position that no round took, including one that finished before the command ran |
| request | `task send` | the turn that took the request in: in Claude Code's record, the turn whose prompts carried the request, and in the others, the first turn to end at or after the record shows the request received |

A request is a prompt the orchestrator hands to Rexume, which delivers it to the worker's conversation tagged with the request's ID; nothing is typed into the pane. A turn the worker finishes before it takes the request in, such as the end of work it was still doing, an interim report, a background job waking it, or a question the user typed, is not the request's answer: it stays untaken, the task counts it as **unread**, and `task next` takes it later, in order. A task has at most one unfinished round.

A round becomes `completed` only when its result is saved in the same transaction that writes its notice: the answer text for an interactive worker, or the result file for a non-interactive run, read before the transaction and up to 1 MiB. A cancel finishes the round as `cancelled` and an error as `failed`; a non-interactive run that exits without a readable result file, or with a nonzero status, is `failed`, and one ended by a signal is `terminated`. A status that leaves `working` without a recorded result does not finish a round. A Claude Code turn the user interrupted, or whose prompt another hook rejected, shows as cancelled only once the worker takes other input, so its round waits until then; the turn that input starts is unread. A request in such a turn stays in the state its send left it in.

When the worker's pane closes, an unfinished round takes a turn the record already shows finished, and otherwise ends as `worker_closed`; `task next` still takes unread turns from a closed pane's record. A record the daemon sees replaced while it follows it, or one now shorter than the position, ends the unfinished round as `failed`, because the turns after the position can no longer be told apart; it is never read again from its start. A worker's record that cannot be read ends the unfinished round as `failed`, with the error in its note, so it holds back neither the other rounds nor a restore; once the record can be read again, `task next` takes the turns after the position.

A process ID means nothing on another server instance, so a run is judged only by its pane's record on the instance it was registered on; a run from before version 3 that the upgrade could not date is judged by its pane's record on any instance. When a new instance appears, before anything is restored, every unfinished round is settled from the earlier instance's records: a round they show ending finishes that way, and a run they leave open ends as `terminated`, because its terminal ended with the server. So does an interactive round they leave open in a worker pane whose conversation the restore does not reopen there, since the pane keeps the shell Rex started and no process would finish the round, unless the conversation runs on in another pane or someone already reopened it in this one; a round left to another pane's restore ends when that restore starts nothing. A worker's pane the new instance does not show was closed before the earlier instance ended, since Rex restores every pane it saved, so the baseline records the close as its close event would have. `add` fails when the daemon started to observe another instance after the worker's instance answered `add`, because that instance has stopped and its runs are already settled.

An unfinished interactive round is `blocked` while its worker is in a **blocked episode**: the task's own conversation has reported `blocked`, a dialog or a question waiting for an answer, from the worker's pane on the server instance the daemon observes, without a break for 1 second, measured from the pane's latest status time as a deadline, so a dialog answered at once makes no episode. The status counts only when its process is that conversation's, so another program that took over the pane neither begins nor keeps an episode. The episode begins in the transaction that sets the round's `blocked_at` and writes its blocked notice. It ends in the transaction of every writer that replaces the pane's status with another or clears it: a status report or its removal, and the reset when the pane first reports on a new instance. The daemon records a whole batch of events before a task pass reads the latest status, so two writes before one pass would otherwise hide one episode's end and the next one's start. A pass that finds the status no longer the conversation's `blocked` on the observed instance ends it too, as does the round finishing; each end also drops the notice if that was not sent. A status recorded on an earlier instance stays in `block`, since restore planning reads it, but neither keeps nor begins an episode, because the worker's process and its dialog went with that server, whether or not the pane is restored; a daemon restart on the same instance keeps the episode. A later block in the same round is a new episode.

### Requests

The command that starts a request round stores the request's text with the round and leaves the delivery to the daemon, the only sender. The daemon sends it once the worker's conversation is the foreground program of its pane on the current server and is neither `working` nor `blocked`, so that the worker takes it as a new turn instead of in the middle of one, through the worker's runtime: the transports of the notices table below, aimed at the worker. Until then it waits as `pending`, with the reason in `note`; a request whose round ends first becomes `superseded` and is never sent. The text starts with `[rexume REQUEST_ID]`, and from there a request moves through a notice's states with their meanings, settled by the worker's record.

What a runtime does with a message it accepted is its own policy, which Rexume does not model: a request stays in the last state Rexume observed until the worker's record shows it received, and its round stays unfinished meanwhile; a request that never arrives, such as one a Claude Code worker held and then dropped, leaves its round unfinished until the owner abandons the round or the worker's pane closes, which ends it as `worker_closed`. Receipts are followed only for unfinished rounds, so a request whose round ended after it was sent keeps the state it had then. `task show` gives the request's state and `task wait` bounds a wait for it.

### Notices

Each finished round has one finished `notice`, and each blocked episode one blocked notice. A running `task wait` decides how it stands in each write transaction it looks in. It registers on the round whenever no live waiter holds it, replacing one that died or returned, takes the round's notices itself, marking each `superseded`, and returns on the first it takes, exiting 3 for a blocked one; a second wait on an episode already reported waits for what comes next. While another live waiter holds the round, it returns when the round finishes or an episode begins that it had not seen when it came to stand behind one, and it watches that waiter's exit, since a waiter that dies writes nothing to the log. Its exit status comes from the transaction that decided to return; the round it prints is read afterwards. So each notice has one claimant, the wait or the daemon, and is never sent again once it may have been; that is not a receipt, since a wait killed after its commit never prints, and two waits running at once may both report the same episode. Acknowledging the round before its finished notice is sent also makes that notice `superseded`, as the end of an episode does for its blocked notice. Otherwise, 3 seconds after the notice was written, which is when the round finished or the episode began, the daemon claims the notice as `sending`, checking in the same statement that no waiter registered since it looked, and sends it through the owner's runtime once the owner conversation is the foreground program of a pane on the current server and is neither `working` nor `blocked`:

| Runtime | Transport | Recorded as |
| --- | --- | --- |
| Claude Code | a user line on the conversation's messaging socket | `sent` |
| Codex | `codex queue --thread ID --message TEXT` | `accepted` when it prints `Queued message` |
| Pi | a file in the inbox the extension watches, which it renames to `.accepted` | `sent`, then `accepted` once renamed |

The notice text starts with `[rexume NOTICE_ID]` and names the round. A finished notice says how many turns are unread when the worker has any; a blocked notice names the worker's pane and says the dialog may have been answered since, and asks for no acknowledgement, since the round goes on. A notice becomes `delivered` only when the owner's own record shows that text as received input: in Claude Code's turn record, a prompt carrying its token whose turn ended with an answer or an error; in Codex, a user response item; in Pi, a `custom_message`. An owner's record that cannot be read is logged and not watched, since a path that cannot be read may not be watchable either and a failed watch would end the epoch; the next pass, whatever starts it, reads it again from its start, since receipts in what was read before the error would otherwise be passed over, and the other owners' records are checked meanwhile. A send that fails before anything leaves, such as a `codex queue` that could not start, goes back to `pending` with the error in `note`, is tried again on the next pass, and is listed with the undelivered notices meanwhile; one that may have gone becomes `unknown` and is settled only by that record, never by a resend. A daemon that starts finds any `sending` row left by its predecessor, which held the same lock, and makes it `unknown`.

An owner gets one notice at a time. The claim records `sent_at`, and the owner's next notice waits while one is `sending`, `sent`, or `accepted` that was sent after the owner's pane last reported its status (`block.status_at`), then until the owner is between turns again. Codex and Pi run one queued message per turn, and Claude Code holds what arrives during a turn, so sending several at once saves no turn; it only moves them from the outbox, where `task wait`, `task ack`, and `task release` can still drop them, into the runtime's queue, where Codex replays them on resume and Pi loses them on exit. A Claude Code owner therefore takes one turn per notice. The owner's record showing the last one releases the next, and so does a status the owner's pane reports after the send, since a runtime that reports one has had its chance to take the notice: a message it dropped, as one held during a turn the user interrupts can be, holds nothing, and neither does one sent to a program whose status the pane no longer has. An `unknown` notice may never have left, so it holds nothing either. A runtime that reports no status is not held.

### Acknowledging and releasing

`task ack` records that the owner has a finished round's result and drops the round's notice if it has not been sent; it does nothing to the worker. Starting a round with `task next` or `task send` acknowledges the round before it in the same transaction. `task abandon` ends a round the owner no longer waits for, as `abandoned`, and acknowledges it in the same transaction: its finished notice is never sent, a request still `pending` is never sent, and one that already left is not withdrawn. It changes nothing for the worker, which may still be running the turn, and does not release the task, so a turn the worker finishes later is unread for `task next`, and the owner can also send a new request. The daemon judges a round only inside a transaction that finds it unfinished, so a round the owner abandoned first stays abandoned. `task release` records that the orchestrator is done with the worker: it acknowledges the latest round, refuses while a round is unfinished or turns are unread, and a released task starts no more rounds. Only a released task's pane is ever closed, so starting a round never races a close.

### Cleanup

The daemon is the only closer of worker panes: for a released task without `--keep-pane`, it claims the pane as `closing` in a short transaction, which fails while any round on that pane is unfinished, and `add` refuses a `closing` pane. It then closes the pane only when every check holds.

The pane's record describes its terminal on the current server instance; a pane not on this instance is gone. A pane recorded on another instance than when the latest result was taken was restored after it, and its generation and status time say nothing about that result. For an interactive worker, the pane's foreground generation is the one recorded with the latest result, its status is neither `working` nor `blocked` and has the status time recorded with the result or is `done`, no conversation reported in the pane since, the worker's record has no turn after the task's position, and the server still shows the worker as the foreground program with such a status. A runtime reports `done` once it finished a turn, which can come after the round took that turn from the record: Claude Code reports it after its `Stop` hooks ran. A worker still `working` after the end its record shows went on as a `Stop` hook told it to, and any other status since the result is use. A non-interactive worker's round ends on the exit of the pane's own program, and Rex starts nothing in a terminal whose program exited, so its pane is unchanged as long as its record still shows the exit. Its generation tells nothing: the server can report an empty foreground after the exit, as it did after a run that printed just before it exited.

The attempt ends as `closed`; as `kept` for good, with the reason in `pane_note`, when the pane was found in use or restored and not closed by the restore; or back to `open` with the reason in `pane_note`, when the pane has focus or the close failed or got no answer, to be tried again when the server's view changes. A successful close forgets the pane in one transaction. A daemon that starts, and each epoch when it starts, puts any `closing` pane back to `open`. A pane a restore held when its epoch ended is then kept once the baseline has recorded it on the current instance, since its record no longer describes the result; one whose epoch ended before that is held again only when it is still unchanged since the result, as at the first hold.

## Limits

Most of these come from what Rex and the agents expose; the others are trade-offs Rexume makes:

- A close carries no reason, so every close on a live server counts as the user's.
- There is no conditional close: a person can take over a worker's pane between the last check and the close.
- There is no per-pane notification audience for a worker's Done or Blocked indicator.
- A blocked notice says only that the worker waits on a dialog or a question: Rexume does not record the kind and message Rex's status carries, and since the notice goes once, the owner may read it after someone answered the dialog.
- `waiter_pid` is a bare pid: when an unrelated process reuses a dead waiter's pid, the daemon leaves the round's notices to it, and a later `task wait` waits behind it, until that process exits.
- Only an interactive worker's round becomes `blocked`; a non-interactive run that waits on a prompt tells its owner nothing.
- Rex starts a shell in every pane it restores and has no way to start another program there instead, so Rexume types into that shell, and a person can start typing between the last read and the line; the line's Ctrl-E and Ctrl-U clear that text instead of running it, except text after the cursor in a vi keymap, and in zsh the earlier lines of a buffer of several when the cursor stands after a blank on a later one. A shell left in vi command mode at an empty prompt looks like one in insert mode and takes the line as commands, so the gate does not run and the restore ends `unknown`. A restored pane shows no earlier exit or output.
- The daemon takes each foreground child of the gate's process for the conversation until it reports itself, so a command a shell function runs after a Codex conversation that exited before its first turn is taken for the conversation, which then reopens in that pane at the next restart.
- A startup file that reads from the terminal, such as one that asks a question, takes the line the terminal holds for the first prompt, so the gate does not run and the restore ends `unknown`.
- Rex saves its sessions about a second after a change, so a change within that second before a crash is not restored.
- `rex` calls outside the adapter and `codex queue` have no deadline, so a server or Codex that never answers holds up the daemon or the task command that called it.
- A notice or request whose send failed before anything left is tried again only on the daemon's next pass, which a change on the server or in the database starts; no timer retries it.
- A restore step that fails on a database or server error leaves the restore in the state it reached, and it is followed again only when the daemon next connects to the server.
- A non-interactive run's exit is attributed to its task by the pane's foreground program at `task add`, so `add` belongs right after the worker starts, and an interactive worker is prompted again only through `task send`.
- A task's first round takes the first turn the worker's process finished, so that an answer finished before `task add` still counts. A process that answered other prompts before the task's hands back the first of those.
- A Claude Code worker whose user interrupts its turn, or whose prompt another hook rejects, stays `running` until it takes other input ([the README's limits](../README.md#known-limits)). So does one whose turn the server's end cut off and that reopens without the continuation prompt; the input it then takes ends that round as `cancelled`. A Stop hook of the user's that makes Claude Code go on after it finished responding ends a turn each time Claude Code stops, so a round takes the first of those answers and the rest are unread.
- Input that reaches a Claude Code turn while it runs carries that turn's prompt ID even when another hook rejects it (observed on Claude Code 2.1.316), so the turn's end shows it received either way. Rexume sends a request or notice only while its conversation is between turns, so this needs the conversation to start a turn in the moment of the send.
- Claude Code passes a `UserPromptSubmit` hook the text Rexume wrote to its messaging socket with its start as written, so the prompt starts with the notice's or request's token (read from Claude Code 2.1.316's executable; its documentation names the event for such a message, not the text's form). If a later version framed that text, no Claude Code turn would show a token: a request to a Claude Code worker would stay `sent` with its round unfinished, and a notice to a Claude Code owner would stay `sent`.
- A running Claude Code picks up the turn hooks an upgrade's daemon adds to its settings file (observed with a project settings file on Claude Code 2.1.316); a turn that ended before then is not in its turn record, so a round waiting for it takes the next turn that finishes. A request the daemon before the upgrade recorded as `delivered` was received before that record starts, so its round takes the first turn the record shows ending; one it had sent but not yet seen received stays `sent`, and its round waits until the owner abandons it.
- A turn that takes a request in also takes whatever other input its runtime merges into the running turn, such as text the user submits in the worker meanwhile, and it is still the request's answer.
- While a request round waits for its answer, turns that finished before the request was taken in are taken only after it, since a task has one unfinished round at a time.
- Claude Code applies its inbound-message rules to notices and requests, which arrive as messages from another session without a permission class; [the README's limits](../README.md#known-limits) give the settings and their defaults. A message Claude Code holds for approval and then drops is never delivered: it stays `sent`, and a held request's round stays unfinished until the owner abandons it or the worker's pane closes. Rexume does not change the setting.
- Codex holds queued input on purpose while a conversation's last turn was interrupted (`turn_aborted` with reason `interrupted` or `budget_limited`) and no turn has run since, in a running session as in one reopened with `codex resume`, so that it does not run on after the user stopped it (observed on Codex 0.164.0). A notice or request sent meanwhile is `accepted` and waits until someone gives the conversation input; Rexume reports it as the record shows it and does not predict the hold, which [openai/codex#56914](https://github.com/openai/codex/issues/56914) asks Codex to expose.
- Pi's inbox, through which notices and requests reach Pi, is under the default state directory.

## Measurements

`cargo test --release --test it bench -- --ignored --nocapture` starts its own server with 20 sessions of three panes each, runs the daemon against it, and prints one JSON report. It runs only on macOS, whose accounting of memory and wakeups it reads. It asserts nothing: read the report against the goals in [AGENTS.md](../AGENTS.md), and a change's report against the baseline commit's from the same machine. `REXUME_BENCH_GOGC` sets `GOGC` for the daemon's `rex do`.

| Key | What it measures |
| --- | --- |
| `idle_30s` | The daemon's CPU seconds and the idle wakeups `top` counts over 30 seconds with nothing happening; both should be 0. |
| `memory_kib` | The daemon, `rex do`, and the relay, each the median of three samples a second apart. `rss` (`ps -o rss`) counts shared and clean file pages in every process that maps them; `phys_footprint` (`top`'s `MEM`) counts what the kernel charges to the process, including compressed pages. `rex do` is Rex's own client and Go runtime. |
| `title_changes_50_calls` | Server calls the daemon made while a pane changed its title 50 times; should be 0. |
| `daemon_children` | The daemon's child processes seen through the title changes and the restore; only `rex do`, one per server instance, is expected, since no process starts per event. |
| `resume_20_conversations_ms` | The time from the new server's start, which restores the sessions itself, until each session's conversation has been claimed by its gate. |
